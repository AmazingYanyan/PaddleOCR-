# 编码工具箱 — Base64 / SHA-256 / 接口测试（v2.0）

一个 Windows 桌面小工具，共五个页签：

- **① 文件 → Base64**、**② Base64 → 文件**、**③ 文本 → SHA-256**：全部在本机离线完成；
- **④ 接口测试**：把选中的 PDF / 图片自动转成 Base64，拼进 `layout-parsing` 请求发给
  PaddleOCR-VL 服务，收回 JSON 并解析结果。

**单个 EXE，免安装，不写注册表，不留后台进程。** 前三页不产生任何网络流量；
第 4、5 页只有在你点「发送请求 / 开始批量」时，才会连你填写的那个地址。

## 二、界面与用法

窗口顶部是五个选项卡。①②③ 彼此完全独立、全部离线；④ 单文件接口测试；⑤ 批量接口测试。

### ① 文件编码 Base64

1. 点「选择文件…」，或**直接把文件拖进窗口**（支持 PNG / JPG / GIF / BMP / WebP / PDF 等任意文件）；
2. 点「开始转换 → Base64」；
3. 下方大文本框直接显示 Base64 全文，底部状态栏给出原文件大小与 Base64 字符数。

- 默认按 **76 字符换行**（MIME 标准），取消勾选即输出一整行；
- 「复制结果」把当前形式的 Base64 放进剪贴板；
- 「保存为 TXT…」把 Base64 存成文本文件，适合超大文件。

### ② 解码还原为文件

1. 把 Base64 内容粘贴进大文本框（**自动忽略空格、换行、全角符号**，标准与 URL-safe 字母表都认）；
2. 「目标文件类型」下拉框默认 **自动判断**——按文件头魔数识别真实类型（PNG/JPEG/GIF/PDF/ZIP/Office 文档等），  
   也可以手动指定目标扩展名；
3. 确认「输出文件夹」（默认桌面，可点「浏览…」更改）；
4. 点「解码并保存到文件夹」，文件以 `decoded_年月日_时分秒.扩展名` 命名保存；
5. 弹窗给出完整保存路径，并可直接打开所在文件夹。

### ③ 文本 SHA-256 摘要

1. 在输入框里输入或粘贴任意文本（支持中文、多行）；
2. 点「生成 SHA-256 摘要」（输入内容变化时也会自动刷新）；
3. 下方文本框输出 64 位十六进制摘要，可切「大写输出」、「复制摘要」。

> 换行统一按 **LF** 计算，保证与其它平台上的文本哈希结果一致。

### ④ 接口测试（PaddleOCR-VL）

这一页是为了联调 `layout-parsing` 接口而做的，一次点击完成
「读文件 → Base64 → 拼请求体 → 发请求 → 解析 → 存图」。

**请求部分（固定在顶部）**

1. **接口地址**：填完整 URL，如 `http://10.1.2.3:8080/layout-parsing`；
   省略 `http://` 也可以，程序会自动补；
2. **方法**：`POST` / `GET`。选 GET 时不发送请求体（参数区内容会被忽略）；
3. **源文件**：点「选择文件…」或把文件拖进本页。选中后立即按扩展名预判 `fileType`
   （PDF → 0，图片/TIFF → 1），发送时还会按文件内容再确认一次；
4. **使用系统代理**：默认**直连**（内网接口一般不需要代理，且能避免 PAC 自动探测卡顿）；
5. **超时**：默认 **10 秒**。单张图/页通常几秒内返回；遇到大 PDF 或服务排队时可以调大。
   界面不会卡死（请求在后台线程里跑）。

**参数部分（中间可滚动区）**

- **功能开关**：17 个布尔参数，勾选后以 `true` 写入请求体，不勾选则该字段**整个省略**
  （不是发 `false`）。其中 `useLayoutDetection` 默认勾选——文档要求正式调用固定为 true。
- **数值 / 枚举**：10 个。`layoutThreshold`（默认 0.3）、`layoutUnclipRatio`（默认 1.5，
  也支持 `[1.1,1.2]` 写法）、`maxNewTokens` 等数值框；`layoutShapeMode`、`layoutMergeBboxesMode`
  是下拉框，避免手写错。
  **留空会自动沿用默认值**；`minPixels` / `maxPixels` 没有默认值，勾选后必须填。
- **手写 JSON 片段**：`markdownIgnoreLabels`、`vlmExtraArgs`、`outputFormats`。
  必须以 `[` 或 `{` 开头且括号成对，否则拒绝发送。

请求体固定以 `{"file":"<base64>","fileType":0|1,...}` 开头，其余参数按上表顺序追加，
Header 只有 `Content-Type: application/json`。

**结果部分（底部）**

- 第一行：`HTTP 200 OK · 耗时 12431 ms · 响应 3.20 MB`；
- 第二行：成功时显示识别到几张图、请求体大小、`fileType`；失败时**红色**显示
  `errorCode` / `errorMsg`（优先取响应体里的，而不是只看 HTTP 状态码）；
- 预览框显示的是**脱敏 + 截断**后的 JSON：图片 Base64 被替换成 `"..."`，超过 64KB 会截断
  并注明；
- **复制响应 / 保存为 TXT…** 由底部「替换 base64」开关决定：勾选则把图片 Base64
  换成 `"..."`（文件小、能直接读），不勾选则保留完整响应（**默认不勾**）；
- 上方预览框**始终**是脱敏 + 截断的：几张图的 Base64 动辄几 MB，塞进编辑框只会卡顿，
  要看完整内容请用「复制响应」或「保存为 TXT…」；
- **保存图片**：把响应里 `outputImages` 与 `markdown.images` 中的图片按文件头（魔数）
  还原成 `ocr_20261022_162013_01.png`（时间戳 + 两位编号 + 真实格式）存到指定文件夹。
  **`inputImage` 会被跳过**（它只是原图回显）。

### ⑤ 批量接口测试

同样是调 `layout-parsing`，区别是「一次挑一个文件夹，把里面的 PDF 和图片全部跑一遍」。

**请求区**

1. **接口地址 / 方法**：与第 4 页各自独立，互不影响；
2. **源文件夹**：点「选择文件夹…」，程序会筛出 `.pdf / .png / .jpg / .jpeg / .bmp / .tif / .tiff / .webp / .gif`，
   其余文件跳过（不递归子文件夹），按文件名排序后列进表格；
3. **类型不用手选**：每个文件在发送时按**文件内容（魔数）**判断，PDF 自动填 `fileType=0`，
   图片自动填 `fileType=1`。表格「类型」列显示的就是这个判断结果；
4. **超时**：默认 **10 秒**，含义同第 4 页。

**参数区**：与第 4 页完全一样的一套控件（17 个开关 + 10 个数值/枚举 + 3 个手写片段），
**只作用于本页**。表格上方就是它，可以滚动。

**执行**：点「开始批量」，**串行**逐个发送（OCR 请求很重，并发会把内网服务和本机内存一起压满）。
表格实时刷新每一行；可随时点「停止」——当前在飞的那一个请求会等它返回，
因为 WinHTTP 是同步阻塞调用，强行中断有 use-after-free 风险。

**结果表格**（`文件名称 / 大小 / 类型 / 图片数 / 用时 / 状态`）

- 第一列是**复选框**，只决定"保存时处理哪些文件"——**请求总是发送全部**；
- 上方有「**全选 / 全不选**」，不用一个个点；
- **图片数**只统计可保存的图片，**已排除 `inputImage`**；
- **用时**单独一列（小于 1 秒按 ms 显示）；
- **状态**只写结果：`完成` / `errorCode=xxx：原因` / `失败：阶段 / 原因`。

**保存**（只处理表格里**勾选**的行；目录就是底部「保存到:」那个，**不会再弹第二次**）

| 按钮 | 产物 | 命名 |
| --- | --- | --- |
| 保存图片 | 每个文件的 `outputImages` 与 `markdown.images` 按魔数还原 | `<源文件主名>_<时间戳>_<序号>.png` |
| 保存为 TXT… | 该文件的响应 JSON | `<源文件主名>_<时间戳>.txt` |
| 替换 base64 | 勾选后，TXT 里的图片 Base64 换成 `"..."`（**本页独立开关**） | 默认不勾 |

> 图片序号是该响应内可保存图片的顺序（从 01 起），`inputImage` 不占号。
> 例：`年报2023_20261022_173012_01.png`、`年报2023_20261022_173012.txt`。

## 三、运行环境

- **Windows 10 / Windows 11**：直接运行，无需任何依赖。
- **Windows 7 SP1 / 8.1**：需要系统已安装 **UCRT（KB2999226）**——该更新自 2015 年起随 Windows Update 普遍推送，  
  绝大多数机器已具备。若目标机器确实没有，请告知，可另行提供不依赖 UCRT 的版本。

EXE 的导入表里只有 Windows 自带组件（`KERNEL32` / `USER32` / `GDI32` / `COMCTL32` / `COMDLG32` /  
`SHELL32` / `ole32` / **`WINHTTP`** 及 UCRT 转发 DLL），**没有任何第三方或编译器运行库**，
也不随包分发任何 runtime。

> `WINHTTP.dll` 是 Windows 自带组件（XP SP2 起），只被第 4 页用来发请求；
> 不额外分发、不需要安装任何东西。

## 四、网络行为与安全说明

这一版新增了接口测试页，所以这里把"会不会联网"说清楚，不留模糊空间。

**① ② ③ 三页完全不联网。** 所有计算都在本进程内完成。

**④ 接口测试页：只在用户点击「发送请求」时发起一次 HTTP/HTTPS 请求。**

| 项 | 说明 |
| --- | --- |
| 目标地址 | 完全由使用者填写，程序里**没有任何硬编码的服务器地址**，也没有默认外发 |
| 发送内容 | 所选文件的 Base64 + 你勾选的参数，Header 只有 `Content-Type: application/json` |
| 触发时机 | 仅「发送请求」按钮；打开软件、切页签、选文件都不会联网 |
| 数据落盘 | 响应只存在内存里；只有你点「保存图片 / 保存为 TXT…」才写文件 |
| 代理 | 默认直连；需要时勾选「使用系统代理」 |

其余行为与上一版一致：

- 不写注册表、不创建服务、不常驻后台、退出后无残留进程；
- 清单声明 `asInvoker`——**以当前用户权限运行，不请求管理员提权**；
- HTTPS 严格校验证书（不提供"忽略证书错误"开关）。若服务端用自签证书，会明确报证书错误；
- 源码可全局搜索确认：网络相关只有 `httpclient.c` 一个文件，且只调用 WinHTTP 的同步 API。

> **提醒**：第 4 页会把文件内容（Base64）发送到所填地址。请在允许的环境里使用，
> 不要指向未经授权的服务。

## 五、拿到文件后怎么验证

### 第 1 步：核对文件完整性（在目标机上）

```bat
certutil -hashfile B64ShaTool_x64.exe SHA256
```

与 `SHA256SUMS.txt` 中的值比对。

### 第 2 步：运行内置自检（推荐，10 秒）

```bat
B64ShaTool_x64.exe /selftest
```

会弹出窗口并显示一份报告：Base64 标准向量、中文往返、1MB 数据往返、SHA-256 官方向量、  
补位边界、百万字节流式处理、文件类型识别等 **32 项断言**。全部通过即表示在这台机器上算法算得对。  
报告同时被复制到剪贴板，便于转交留档。

### 第 3 步：结构体检（可选，在开发机上）

```bash
python3 tools/verify_exe.py dist/B64ShaTool_x64.exe
```

检查 PE 头、GUI 子系统、图标/版本/清单资源齐全、清单配置正确、导入表无非系统 DLL、中文以 UTF-16 正确写入。

### 第 4 步：界面几何自检（界面显示异常时用）

```bat
B64ShaTool_x64.exe /diag
```

弹窗列出主窗口客户区、屏幕位置与可见状态、选项卡内容显示区、三个面板与每个关键控件的  
**真实位置与尺寸**，另附**界面构建诊断**（是否已构建、构建时用的父窗口、控件创建失败次数与错误码）  
和一行**布局校验结论**（通过 / 未通过），并把同样内容复制到剪贴板。  
界面若有异常，把这段文本回传即可精确定位。

### 第 5 步：端到端编码自检（编码功能异常时用）

```bat
B64ShaTool_x64.exe /enc-test "C:\路径\某个图片.png"
```

不点界面，直接把"读文件 → Base64 编码 → 写进文本框 → 从文本框回读解码 → 与原始文件逐字节比对"
整条链路跑一遍，并逐段回显结果与结论：

```
[1] 读取文件 ......... 磁盘 409600 字节 / 读入 409600 字节  →  OK
[2] Base64 编码 ...... 期望 546136 字符 / 实际 546136 字符  →  OK
[3] 写入文本框 ....... 文本框共 560503 字符（含换行），其中有效 Base64 字符 546136 个  →  OK
[4] 回读解码一致性 ... 解码得到 409600 字节 / 原文件 409600 字节  →  逐字节一致 OK
结论: 全部通过 —— 该文件的编码链路正常
```

任何一步异常都会明确指出是在第几步、失败原因是什么。报告同时复制到剪贴板。

### 第 6 步：接口链路自检（接口测试页异常时用）

```bat
:: 先不联网，只验到"组装请求体"这一步
B64ShaTool_x64.exe /api-test "D:\样本\年报.pdf" /url:http://10.1.2.3:8080/layout-parsing /dry

:: 真发一次，并把返回的图片存下来
B64ShaTool_x64.exe /api-test "D:\样本\年报.pdf" ^
    /url:http://10.1.2.3:8080/layout-parsing /method:POST ^
    /outdir:D:\ocr_out /save
```

可选参数：`/method:GET|POST`、`/filetype:auto|0|1`、`/timeout:180`、
`/param:useLayoutDetection=true`、`/param:layoutThreshold=0.3`、
`/raw:markdownIgnoreLabels=["number"]`、`/proxy`、`/report:D:\report.txt`。

输出形如：

```
[/api-test 接口链路自检]
源文件   : D:\样本\年报.pdf
目标 URL : http://10.1.2.3:8080/layout-parsing   方法 POST

[1] 读取文件 ......... 409600 字节（38 ms）→ OK
[2] 类型识别 ......... .pdf → fileType=0 → OK
[3] Base64 编码 ...... 546136 字符（12 ms）→ OK
[4] 组装 Body ........ 546310 字节 → OK
    SHA-256: 9f2c1a3b7d4e5f60…
[5] 发送请求 ......... HTTP 200 OK，用时 12431 ms，响应 3.20 MB → OK
[6] 解析响应 ......... errorCode=0 Success → OK
[7] 提取图片 ......... 4 张可保存（已排除 inputImage）→ OK
[8] 保存图片 ......... 保存 4 张，失败 0 张。共 3.1 MB
    目录：D:\ocr_out
[9] 脱敏副本 ......... 3355443 → 32110 字节 → OK

结论: 全部通过 —— 该文件到该接口的整条链路正常
```

失败时会写明第几步、阶段、错误码与已收字节数。报告同时复制到剪贴板。

### 2026-10-22（v2.1.0）：新增第 5 页「批量接口测试」

**需求**：一次挑一个文件夹，把里面的 PDF / 图片批量发给 `layout-parsing`；
不逐张展示，只看一张结果表（复选框 / 名称 / 大小 / 类型 / 图片数 / 状态）；
保存时只处理表格里勾选的行。

**关键设计**

1. **参数区做成可实例化组件**（`param_ui` + `params_*`）。原先 30 个控件、滚动、
   默认值、取值都挂在单例 `A` 上；批量页需要第二套且两页互不影响。
   重构后 `params_build / defaults / collect / layout / scroll / on_command` 都接受
   `param_ui*`，第 4 页用 600 号段、第 5 页用 900 号段，各自独立、互不干扰。
2. **串行执行**。单个 OCR 请求几十秒，并发会把服务端和本机内存一起压满；
   串行还能让进度与错误精确对应到具体文件。worker 线程只是循环调 `api_run()`，
   每返回一个文件就 `PostMessage` 一行回来刷新表格。
3. **停止是"软停止"**：置标志后等当前请求返回再收尾。WinHTTP 是同步调用，
   强行打断会留下悬空句柄。
4. **表格用 ListView（`LVS_EX_CHECKBOXES`）**，原生复选框，不需要自绘；
   「图片数」按 `inputImage` 过滤后再统计。

**改动面**：`main.c` 面板数 4→5、新增 `WM_BATCH_ROW/WM_BATCH_DONE`、滚动/滚轮/拖放/通知
分流、`ICC_LISTVIEW_CLASSES`；`apitest.c` 新增批量页；`apitest.h` 新增 `IDB_*` 号段与接口。

**顺带调整**：超时默认值 180 → **10 秒**（第 4、5 页）。

### 2026-10-22（v2.0.1）：修第 4 页的 5 处实测问题

### 2026-10-22（v2.0）：新增第 4 页「接口测试」

**需求**：联调 PaddleOCR-VL 的 `layout-parsing` 接口——选文件后自动转 Base64 拼进请求、
发出去、拿到 JSON、把返回的图片一键存下来、还能把 Base64 脱敏后存成 txt。

**新增模块**（都在 `2.0/src/`）：

| 文件 | 职责 |
| --- | --- |
| `jsonlite.c` | 容错 JSON 扫描。不建树、只记偏移，遇到截断/非 JSON 也不会崩。图片判定用四重条件（长度、字符集、4 的倍数、**解出来看魔数**），避免把 Markdown 正文误判成图片 |
| `apibody.c` | 30 项参数表 + 值校验 + 请求体拼接。数值严格按 JSON 数字文法校验（`1.`、`.5`、`007` 一律拒绝，否则会拼出非法 JSON） |
| `httpclient.c` | WinHTTP 薄封装。默认直连、可配超时、流式读响应、大 body 失败时回退分块写、错误码翻译成中文 |
| `apitest.c` | 第 4 页界面（含滚动参数区）、工作线程、结果渲染、存图/存 TXT、`/api-test` 命令行自检 |

**两个关键设计决定**

1. **必须用工作线程**。WinHTTP 是同步阻塞的，`WinHttpReceiveResponse` 内部阻塞时无法处理
   任何窗口消息——沿用原来「阻塞 + `pump()`」的做法，界面会直接「未响应」。
   现在界面线程派活、worker 只投递一条 `WM_API_DONE`，全程不碰窗口句柄；
   代际号丢弃过期结果，关窗前二次确认。
2. **参数区必须能滚动**。30 项参数排下来约 480px，而面板扣掉请求区和响应区只剩约 300px。
   用一个复用 `B64Panel` 类的子窗口承载参数，配独立 `SCROLLBAR`，靠 `DeferWindowPos`
   整体平移，不引入子类化。

**踩到的坑（都已修）**

- 枚举值写进 body 时漏了引号，拼出 `"layoutShapeMode":quad` 这种非法 JSON。
  单测里的"精确字符串比对"抓到了它。现在枚举一律带引号，数值与 JSON 片段才是裸 token。
- 数值校验最初用 `strtod` + "是否被完整消费"判断，结果 `1.`、`.5`、`007` 都能通过——
  拼出来的 JSON 是非法的。改为按 JSON 数字文法逐字符校验。
- `WinHttpCrackUrl` 返回的路径/主机名长度单位是**字符**不是字节，最初按字节算会把路径砍一半。
- 预览截断在逗号处断开时没把逗号本身留下，预览末尾会多出一个悬空的引号。
- `verify_exe.py` 的 DLL 白名单没有 `winhttp.dll`，而 `build.sh` 开了 `pipefail`，
  不改会直接让构建失败（已加入，并确认导入表里确实出现了 `WINHTTP.dll`）。

**刻意没做的**（避免范围失控）：请求历史/重发、`file` 传 URL 而非 Base64、自定义 Header、
忽略证书错误的开关（目标为 HTTP 明文）、配置持久化（工具承诺不写注册表）。

### 2026-10-13（第 4 版）：修复"选好图片点开始转换，程序直接退出"

**现象**：Windows 10 22H2。解码还原、SHA-256 摘要两个功能都正常；  
"文件 → Base64"这条路径上，一张约 400KB 的 PNG 可以选中、能显示文件大小，  
但一点「开始转换 → Base64」**程序立即退出**（进程消失，不是窗口关闭）。

**根因**：`read_whole_file()` 里把 `size_t` 变量的地址强制转换成 `LPDWORD` 交给了 `ReadFile`。

```c
size_t total = 0, want, got;                    /* got 是 8 字节 */

if (!ReadFile(h, buf + total, chunk, (LPDWORD)&got, NULL)) { ... }
total += got;                                   /* 读到了一个天文数字 */
...
buf[total] = 0;                                 /* ← 越界写入，访问违例 */
```

`ReadFile` 的第 4 个参数是 `LPDWORD`，**只写 4 个字节**；而 x64 下 `size_t` 是 8 字节，  
**高 4 字节始终保持栈上的未初始化垃圾值**。于是：

1. `total += got` 得到一个天文数字，`while (total < want)` 立即退出循环；
2. 紧接着执行 `buf[total] = 0`，向 `buf + 天文数字` 写入 —— 该地址不在任何已提交的内存里，
   触发**访问违例（0xC0000005）**，Windows 直接终止进程。

反汇编证据（`x86_64`，`clang -O2`，事故版本）：

```asm
callq *%rdi              ; ReadFile(h, buf+total, chunk, &got, NULL)
movq  0x38(%rsp), %rax   ; ← 按 8 字节读取 got 所在槽位（高 4 字节是垃圾）
addq  %rax, %rbx         ; total += got
movb  $0x0, (%r15,%rbx)  ; buf[total] = 0   ← 越界写入，崩溃点
```

同文件里的 `write_whole_file()` 用的是正确的 `DWORD wrote`，所以**解码保存文件一直是好的**——  
这也正是"只有编码功能崩"的原因：只有它会去读文件。

**修复内容**：

1. `read_whole_file()` 里改用**真正的 `DWORD got = 0;`** 接收字节数，
   `ReadFile(..., &got, ...)` 不再做任何强制转换；
2. 读取循环后增加一道**越界防御**：若 `total > want` 直接报错返回，绝不落到 `buf[total] = 0`；
3. `wrap_text()` 的 `malloc` 补上失败判断；`render_b64_to_box()` / `current_b64_text()`
   同步处理空指针（此前内存不足时也会越界写）；
4. 新增 `tools/check_io_types.py` 静态校验并接入构建流程（见下）；
5. 新增 `tests/test_pipeline.c` 编码链路回归测试；
6. 新增 `/enc-test "<文件>"` 命令行端到端自检；
7. 版本资源升级为 `1.0.0.4`。

**修复后的机器码**（同一位置，同一个编译选项）：

```asm
callq *%r13              ; ReadFile(h, buf+total, chunk, &got, NULL)
movl  0x3c(%rsp), %eax   ; ← 只读 4 字节，高 32 位自动清零
testq %rax, %rax
je    ...                ; got == 0 → 跳出
addq  %rax, %rbp         ; total += got（干净值）
...
cmpq  %r12, %rbp
jbe   ...                ; 越界防御：total > want 时走错误分支
```

**为什么第 3 版没能发现**：第 3 版修的是界面构件，用户当时连按钮都点不到，这条路径从未被执行过。  
这也说明"只能靠静态推理验证 GUI"是有风险的，所以这次补上了 `/enc-test` 这类**目标机可自跑的端到端检查**。

### 2026-10-13（第 3 版）：修复"界面依然全空白"——控件根本没被创建

**现象**：Windows 10 22H2，两台机器表现一致：窗口正常出现，客户区内空无一物。  
`/diag` 回传的关键信息：**主窗口客户区 1104×781（窗口本身是好的），但 `tab`、`status`、  
`panel[0..2]` 全部显示 `<未创建>`**。

**根因**：`build_ui()` 把所有控件的父窗口写成了全局变量 `g_hMain`，而它是在 `WM_CREATE` 里被调用的；

```c
g_hMain = CreateWindowExW(...);   /* 赋值要等 CreateWindowExW 返回之后才发生 */
```

也就是说 **`WM_CREATE` 执行期间 `g_hMain` 仍然是 `NULL`**。Microsoft 官方文档  
《Window Features》对此有明确结论：

> If you specify the `WS_CHILD` style in `CreateWindowEx` but do not specify a parent window,  
> the system **does not create the window**.
> （指定了 `WS_CHILD` 却没有给出父窗口时，**系统不会创建该窗口**。）

于是选项卡、三个面板、状态栏和全部输入框/按钮**每一个都创建失败并返回 `NULL`**。  
窗口壳子本身创建成功，所以能显示、能响应 `/diag`，客户区里却什么都没有 —— 与现象完全吻合。  
> 这也解释了为什么第 2 版的修复没有任何效果：布局再怎么算，也是在一堆不存在的控件上做无用功。

**修复内容**：

1. `build_ui()` 改为 `build_ui(HWND parent)`，**父窗口由调用方显式传入**，不再读全局变量；
2. `WM_CREATE` 里用消息自带的 `h`（就是主窗口本身）作为父窗口构建界面；
3. 主窗口创建完成、`g_hMain` 已是有效句柄后，**再兜底构建一次**，由 `g_uiBuilt` 标志去重 ——  
   即使某些系统上 `WM_CREATE` 的构建没走通，还有第二次机会；
4. 界面建好后**自检关键控件句柄**，任一为 `NULL` 就弹出错误框并列出失败次数、错误码、  
   失败控件类名与各句柄值 —— **宁可弹一个说得清原因的错误，也不再留一片空白**；  
   若同时带 `/diag`，则不退出，把失败详情并入几何自检一起回显；
5. `layout()` 增加主窗口句柄有效性判断，避免在窗口尚未创建时读取未初始化的矩形；
6. `mk()` 增加"父窗口无效"显式记账，不再静默失败；
7. 启动时把 `SW_HIDE` 兜底为 `SW_SHOWNORMAL`（计划任务 / RPA 宿主可能传入隐藏标志），  
   并在首次布局后 `RedrawWindow(..., RDW_ALLCHILDREN | RDW_UPDATENOW)` 强制连同子窗口重绘一遍；
8. `/diag` 增补：主窗口屏幕位置与可见/最小化状态、"构建时父窗口与主窗口是否一致"、  
   控件创建失败统计、以及一行布局校验结论。
9. **新增 `tools/check_ui_parent.py`，并把"界面构建静态校验"接进 `build.sh`（第 3/7 步）** ——  
   本机跑不了 Windows GUI，就用静态分析把"父窗口传递"这条性质钉死：校验 `build_ui` 形参、  
   函数体内是否误用 `g_hMain`、所有 `WS_CHILD` 窗口是否都有有效父窗口、调用点是否已校验句柄。  
   不通过就直接中止构建。（已用"人为改回旧写法"做过反向验证，确认它真能抓出该 bug。）
10. **构建可复现**：链接时加 `-Wl,--no-insert-timestamp`，不再把构建时间写进 PE 头 ——  
    否则同一份源码每次构建出来的 SHA-256 都不同，"传输后核对校验值"就失去了意义。

> 算法核心（`b64sha.c` / `selftest.c`）未改动：单元测试 173 项、内置自检 32 项全部通过，  
> `-Wall -Wextra -Wshadow -Wconversion` 零告警，clang `--analyze` 零发现。

### 2026-10-13（第 2 版）：修复"窗口打开后整片空白"（**未解决，见上方第 3 版**）

**现象**：目标环境 Windows 10 22H2，双击运行后窗口正常出现，但客户区一片空白，看不到任何控件。  
文件 SHA-256 与交付值一致，排除文件损坏。

**根因（两个缺陷叠加，另有一个隐藏的坐标反向 bug）**：

1. **`layout()` 从未被执行过**。布局只挂在 `WM_SIZE` 上，而窗口是用 `CreateWindowExW` 创建、  
   **没有带 `WS_VISIBLE`**；创建阶段尺寸未发生变化，系统不会派发 `WM_SIZE`；随后 `ShowWindow`  
   只改变可见性、尺寸也没变，同样不派发 `WM_SIZE`。于是所有控件停留在"刚创建时的 `10x10`"，  
   而 `100x100` 的选项卡与状态栏全被压在左上角，整片客户区只剩主窗口底色 —— 看上去就是空白。
   > 网上多数 Win32 示例代码之所以不会踩到，是因为它们把 `WS_VISIBLE` 直接写进了  
   > `CreateWindowEx` 的样式里，系统便会在创建阶段派发一次 `WM_SIZE`。
2. **三个面板从来没有被 `MoveWindow` 过**。面板创建时是 `100x100` 固定在 `(0,0)`，  
   而全部控件都是面板的**子窗口**，会被裁剪到父窗口客户区内 —— 即使 `layout()` 跑了，  
   控件也只能在左上角 100×100 的方块里露出一点边角。此前只移动了面板里的控件，  
   漏掉了面板自身。
3. **`TCM_ADJUSTRECT` 参数用反**。该消息 `wParam=TRUE` 表示"传入选项卡窗口矩形、返回内容显示区"，  
   `FALSE` 表示"传入内容显示区、返回窗口矩形"。原代码用 `FALSE`，得到的是向上越界的负坐标，  
   会把面板顶到页签上方（页签既看不见也点不动）。已改为 `TRUE`，并加了兜底：  
   若返回的矩形不合理（`top<=0` 或宽高非正），退回一套保守值，保证界面一定能出来。

**修复内容**：

- 在窗口真正显示出来之后（`ShowWindow` + `UpdateWindow` 之后）**显式调用一次 `layout()`**，  
  不再依赖 `WM_SIZE` 的投递时机；`WM_CREATE` 末尾也统一走一次 `switch_tab(0)`，  
  形成"`WM_CREATE` → 显示后显式布局 → `WM_SIZE`"三重保障，任一条路径生效即可。
- `layout()` 中把三个面板 `MoveWindow` 到选项卡内容显示区，面板内控件改用面板坐标系（原点 `0,0`）。
- 修正 `TCM_ADJUSTRECT` 方向，并增加矩形合理性校验与兜底。
- 新增界面几何自检 `/diag`。
- 主窗口加 `WS_EX_CONTROLPARENT`，使 `Tab` 键能在三个面板之间正常轮转焦点。

> 说明：本次修改只涉及界面几何与消息时序，**算法核心（Base64 / SHA-256）未改动**，  
> 单元测试 173 项、内置自检 32 项依旧全部通过。

## 九、已知限制与设计取舍

| 项目           | 现状                    | 原因                                                   |
| ------------ | --------------------- | ---------------------------------------------------- |
| 单文件上限        | 1 GB                  | 超出后内存占用不划算，且 Base64 会膨胀到 1.33 GB                     |
| 文本框预览上限      | 600 万字符（约 4.5 MB 源文件） | 超长文本塞进编辑框会明显卡顿；超限时文本框给出提示，完整内容仍可通过「复制结果 / 保存为 TXT」获取 |
| Base64 换行    | 默认 76 字符换行            | MIME 标准，任何规范解码器都接受换行；需要长单行时取消勾选即可                    |
| SHA-256 换行归一 | CRLF → LF             | 避免同一段文本在 Windows 与 Linux 上算出不同摘要                     |
| 解码容错         | 静默忽略非 Base64 字符       | 从邮件/文档里复制常混入空格与全角符号；**忽略的字符数会在结果弹窗中明示**              |
| 输出文件名        | 时间戳自动命名               | 避免覆盖既有文件；同秒冲突时自动追加 `(1)`、`(2)`                       |
| DPI          | 声明为 DPI 感知并按比例缩放      | 高分屏下界面清晰不模糊                                          |
| 接口测试并发     | 同一时间只允许一个请求          | 界面按"发送"即禁用相关控件，避免连点造成两个请求互相覆盖结果                  |
| 请求取消       | 不提供取消按钮              | 跨线程关句柄有 use-after-free 风险；改用可配置超时（默认 10 秒）兜底          |
| 响应大小上限     | 128 MB（32 位 64 MB）    | 防止 `visualize=true` 的异常响应把内存打爆；超限会明确报出来                |
| 请求体大小上限    | 48 MB                 | 对应约 32 MB 源文件；超限在发送前就拒绝，不会发出半个请求                       |
| 接口测试参数记忆   | 每次启动恢复默认             | 工具承诺不写注册表，因此不做配置持久化                                    |
| 参数区滚动      | 滚动条为主，滚轮为辅          | 共 30 项参数一屏放不下；滚轮在焦点落到子控件时可能不响应，用滚动条即可            |

> `.toolchain/` 目录只是构建工具链的落地位置，**与运行无关，可以整个删除**（其中 `x/`、`dl/`、`libs/`  
> 是早期尝试的失败产物，`llvm/` 是当前使用的工具链）。
